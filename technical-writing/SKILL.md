# Technical Writing 가이드라인

이 스킬은 Toss의 [technical-writing.dev](https://technical-writing.dev) 가이드라인을 기반으로 한다.
문서를 작성하기 전에 아래 단계를 따른다. 기존 문서 리뷰 요청이면 Step 1~3을 리뷰 기준으로 사용한다.

---

## Step 1: 문서 유형 결정

다음 세 가지를 파악한다. 대화에서 이미 파악됐거나 요청 자체로 자명하면 질문하지 말고 스스로 판단한 뒤 선택한 유형과 근거를 사용자에게 알린다.

- **문서 목적**: 독자가 이 문서로 무엇을 하려고 하는가?
- **독자 수준**: 초보자인가, 이미 기본을 아는 사람인가?
- **프로젝트 상황**: 새로 도입인가, 기존 시스템 개선인가?

### 유형 A: 학습 중심 문서 (튜토리얼)
> "새로운 기술을 처음 접해서 흐름을 파악하고 싶다"

**구조**: 학습 목표(완료 후 할 수 있는 것) → 사전 요구사항·환경 설정 → 단계별 가이드 → 최종 확인
**핵심 원칙**:
- 처음부터 끝까지 막힘 없이 따라올 수 있어야 한다
- 실제로 실행 가능한 코드 예제 필수 — 간단한 것에서 시작해 난이도를 점진적으로 올린다
- 핵심 학습 경로에 집중하고 곁가지 내용은 최소화한다
- FAQ 섹션으로 자주 막히는 지점을 보완한다

### 유형 B: 문제 해결 문서 (How-to / 트러블슈팅)
> "특정 문제를 빠르게 해결하고 싶다"

**구조**: 문제 정의 → 원인·배경지식 → 단계별 해결 방법 → 확인 방법
**핵심 원칙**:
- 에러 메시지·로그 예시를 포함해서 독자가 자신의 상황인지 바로 파악하게 한다
- 코드보다 설명이 먼저 온다 — 코드가 먼저 나오면 인지 부하가 생긴다
- "왜 이렇게 해야 하는지" 해결책의 원리도 설명한다
- OS, 라이브러리 버전 등 환경별 차이를 고려한다

### 유형 C: 참조 문서 (Reference)
> "기본은 알고 있고, 특정 API·옵션을 빠르게 확인하고 싶다"

**구조**: 간결한 개요 → 시그니처·파라미터(타입, 기본값, 필수 여부) → 반환값·타입 → 사용 예제(기본 → 다양한 활용) → 주의사항·제한사항 → 관련 API 링크
**핵심 원칙**:
- 정보는 정확하고 완전해야 한다 (누락 없음)
- 일관된 포맷으로 탐색이 쉬워야 한다
- 다양한 사용 사례를 예제로 제공한다

### 유형 D: 설명 문서 (깊은 이해)
> "개념·원리·배경 지식을 깊이 이해하고 싶다"

**구조**: 개념 소개 → 등장 배경(해결하려는 문제) → 작동 방식 → 다른 접근 방식과의 비교 → 활용 사례
**핵심 원칙**:
- 기술이 왜 등장했는지, 어떤 문제를 해결하는지부터 설명한다
- 다이어그램, 흐름도, 표로 복잡한 개념을 시각화한다
- 독자가 납득할 수 있도록 설득력 있게 서술한다

### 유형 판단 예시

| 요청 주제 | 유형 |
|-----------|------|
| "JavaScript this 키워드의 동작 방식" | D 설명 (원리·등장 배경) |
| "Webpack에 HtmlWebpackPlugin 설정 추가하는 법" | B 문제 해결 (단계별 구현) |
| "React Hydration 오류 해결" | B 트러블슈팅 (원인 분석 + 해결책) |
| "Node.js fs.readFile의 options 파라미터" | C 참조 (세부 사양) |
| "우리 팀에 Playwright 처음 도입하기" | A 학습 (시작 가이드) |

**유형은 조합해도 된다.** 템플릿에 얽매이지 말 것 — 예: 설명 문서 끝에 참조 표를 붙이거나, 튜토리얼에 트러블슈팅 섹션을 두는 것은 자연스럽다. 단, 조합하더라도 문서의 주된 목적 하나는 분명해야 한다.

## Step 2: 정보 구조 적용

유형을 결정했다면 아래 6가지 원칙에 따라 문서 구조를 설계한다.

| 원칙 | 체크 포인트 |
|------|-------------|
| **한 페이지, 하나의 주제** | `####(H4)` 이상의 제목이 생기면 문서를 분리한다. 핵심 주제가 2개 이상이면 별도 문서로 나눈다. 여러 개념을 소개해야 하면 개요 페이지를 만들고 개별 문서로 링크한다 |
| **가치를 먼저** | 도입부에서 독자가 얻을 이점을 먼저 제시한다. 도입 연혁·설정 옵션 나열은 후순위. ❌ "이 설정은 2019년에 도입되었고…" → ✅ "이 설정을 적용하면 네트워크 지연을 최소화할 수 있어요" |
| **효과적인 제목** | 독자가 검색할 핵심 키워드 포함, 30자 이내, 물음표·느낌표 없는 평서문, 같은 레벨은 문체 통일(동사형이면 전부 `~하기`, 명사형이면 전부 명사형). ❌ "에러를 해결하는 방법은?" → ✅ "NOT_FOUND_USER 에러 해결하기" |
| **개요 필수** | 제목 바로 아래에 1~3문장 개요. "이 문서를 읽으면 무엇을 할 수 있는가?"에 답해야 하고, 개요만 읽어도 주제를 알 수 있어야 한다 |
| **예측 가능한 구조** | 기본 개념 → 구체적 사용법 → 예제 → 심화 순서(단순 → 복잡). 각 섹션은 설명을 먼저, 코드를 나중에. 같은 수준의 섹션은 같은 패턴으로 |
| **자세히 설명** | 새 개념은 처음 등장할 때 1~2문장으로 정의하고 왜 필요한지 밝힌다. 동작 조건·입력·상황별 결과 차이를 명시하고, 시간·크기 값에는 단위를 붙인다(예: "duration: 세션 지속 시간(밀리초). 자동 로그아웃 시에는 마지막 활동 시각까지 계산") |

## Step 3: 문장 원칙 (작성 중 체크)

문서를 작성하면서 다음 5가지 원칙을 지킨다.

### 1. 주체를 분명히
- 도구·시스템이 아닌 **사람(독자)을 주체**로 쓴다
- 수동형 대신 능동형을 사용한다

> ❌ "설정이 완료되어야 합니다"
> ✅ "설정을 완료하세요"

> ❌ "이 라이브러리는 DB 초기화를 수행해요"
> ✅ "이 명령어를 실행하면 DB를 초기화할 수 있어요"

### 2. 필요한 정보만
- **한 문장, 하나의 생각** — 길어진 문장은 둘로 나눈다
- 메타 담화("말에 대한 말")를 제거한다: "다음으로", "앞서 설명했듯이", "결론적으로", "아시겠지만"

> ❌ "앞에서 설명했지만, 결론은 이 설정을 변경하는 것이 가장 효과적이라는 겁니다"
> ✅ "이 설정을 변경하는 것이 가장 효과적입니다"

### 3. 구체적으로
- 명사 → 동사: "배포 수행이 필요" → "배포하세요"
- 모호한 표현 → 구체적 수치·결과: "데이터가 많을 때" → "10,000건 초과 시", "영향을 받을 수도 있음" → "설정이 삭제됨"
- 누가·무엇을·어디서·어떻게를 명시: "자동으로 저장됨" → "서버에 자동 저장됨"
- 업계 은어 대신 실제 동작: "Exception을 던짐" → "예외를 일으킴"
- 단계 간 참조 맥락을 연결: "1단계에서 저장한 API 키를 3단계에서 사용합니다"

> ❌ "일부 브라우저에서 동작하지 않을 수 있습니다"
> ✅ "Internet Explorer에서는 동작하지 않습니다"

### 4. 자연스러운 한국어
- 빼도 의미가 통하는 한자어 동사 제거: "수행합니다", "진행합니다"
- 번역체(-tion/-ing 명사구, "~를 통해") → 동사 중심으로

> ❌ "로그 파일을 삭제하는 작업을 수행합니다"
> ✅ "로그 파일을 삭제합니다"

> ❌ "API 키를 이용한 사용자 인증 처리가 완료된 후"
> ✅ "API 키로 사용자를 인증한 후"

> ❌ "이 API를 통해 데이터를 가져올 수 있습니다"
> ✅ "이 API로 데이터를 가져올 수 있습니다"

### 5. 일관되게
- 공식 기술 용어를 사용한다 (위키피디아·공식 문서 표기 기준, 대소문자 포함): "K8" → "쿠버네티스(Kubernetes)"
- 같은 개념은 하나의 표현으로만 쓴다: "추가/첨부/넣기" 혼용 → "업로드"로 통일
- 약어는 처음 등장할 때 풀어쓴다: `SSR(Server-Side Rendering)`
- 외래어는 맞춤법보다 업계 관행을 따른다 (구글 트렌드에서 압도적으로 많이 쓰이는 표기 채택): "프런트엔드" ❌ → "프론트엔드" ✅
- **문체(해요체/합니다체)를 문서 전체에서 하나로 통일한다.** 기존 문서에 이어 쓰면 그 문체를 따르고, 새 문서면 사용자 요청·대상 독자에 맞춰 하나를 정한다
- 본문에 이모지를 쓰지 않는다

## Step 4: 멀티 페이지 문서 구조 (해당 시)

한 페이지로 끝나지 않는 문서(문서 사이트, 위키 섹션, docs/ 폴더)를 설계할 때 적용한다. 단일 문서면 건너뛴다.

1. **왼쪽 내비게이션 메뉴를 짠다고 생각하고 페이지 목록을 먼저 설계한다** — 각 페이지는 Step 1의 유형 중 하나를 맡는다
2. **기본 템플릿**에서 시작해 필요 없는 것은 뺀다:

```
docs/
├── get-started.md      # 시작하기 (학습)
├── tutorials/          # 학습 중심
├── how-tos/            # 문제 해결
├── explanations/       # 개념 설명
├── reference/          # 참조
├── troubleshooting.md  # 트러블슈팅
└── glossary.md         # 용어집
```

3. **크로스링크를 설정한다** — 관련 페이지끼리 본문에서 서로 링크해 독자가 자연스럽게 탐색하게 한다 (예: 코드 분할 문서에서 lazy loading 문서로)

## 실행 흐름

```
1. 문서 유형 파악 (자명하면 스스로 판단, 모호하면 사용자에게 질문)
   ↓
2. 선택한 유형·구조를 사용자에게 알리고 작성 시작
   (여러 페이지 문서면 Step 4로 페이지 목록부터 설계)
   ↓
3. 정보 구조 6원칙에 따라 섹션 배치
   ↓
4. 문장 5원칙을 지키며 실제 내용 작성
   ↓
5. 작성 후 3단계 셀프 리뷰 (유형 → 구조 → 문장 순서로 점검)
```

## 최종 셀프 리뷰 (3단계)

**① 유형 리뷰**
- [ ] 문서 유형이 독자 목적에 맞는가? 유형을 조합했다면 주된 목적 하나가 분명한가?
- [ ] 모든 코드·명령어는 실제로 실행 가능한가?

**② 구조 리뷰**
- [ ] 개요만 읽어도 무슨 문서인지, 읽으면 무엇을 할 수 있는지 알 수 있는가?
- [ ] H4 이상의 제목이 생기지는 않았는가? (생겼으면 문서 분리)
- [ ] 도입부에서 가치(이점)를 먼저 제시했는가?
- [ ] 같은 레벨 제목의 문체가 통일되어 있고, 각 섹션이 설명 → 코드 순서인가?
- [ ] 새로운 개념을 처음 등장할 때 정의했는가? 단위·동작 조건을 명시했는가?

**③ 문장 리뷰**
- [ ] 수동형, 번역체, 불필요한 한자어, 메타 담화가 없는가?
- [ ] 모호한 표현("일부", "~할 수 있음") 대신 구체적 수치·결과를 썼는가?
- [ ] 같은 개념을 여러 표현으로 쓰지 않았는가? 문체가 하나로 통일됐는가?
